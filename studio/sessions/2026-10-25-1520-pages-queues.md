## Summary
`/go` found main's last Pages deploy (#45) cancelled, so the live site and studio page were stale: a failed deploy, top of the pick list. Filed [#47](https://github.com/thesnwmn/pixelbob/issues/47) and fixed it: main's deploy has its own queue, and nothing that pushes to `gh-pages` overwrites another push.

## Done
- `deploy-pages.yml`: concurrency group `gh-pages-site`, the deploy action with `force: false` and `attempt-limit: 10`, so it rebases onto a preview that pushed first.
- `pr-preview.yml` and `pr-cleanup.yml`: one group per PR, `gh-pages-pr-N`. The preview's deploy action rebases the same way; the cleanup, on a rejected push, fetches the new tip and removes the folder again (up to 10 tries).
- `github/pages` health check (`scripts/health/src/github.ts`), with fixtures: the site's group is its own, the deploy action never force-pushes, a raw `git push` to `gh-pages` refetches on rejection. On the old workflows it reports all five problems.
- Docs: [hosting and previews](../../docs/tech-and-toolchain.md#hosting-and-previews), and the check in the [health tiers](../README.md#health).

## Learned
- GitHub keeps one running and one pending run per concurrency group, and a new pending run cancels the older one, whatever workflow it's from. `cancel-in-progress: false` only protects the running one. A merge that opens the next PR at once queues four `gh-pages` runs.
- `JamesIves/github-pages-deploy-action` force-pushes by default (`force: true`). It was harmless only because the shared queue serialised everything. With `force: false` it fetches and rebases on a rejected push.
- The cleanup's checkout is shallow, so it starts again from the new tip rather than `pull --rebase`.
